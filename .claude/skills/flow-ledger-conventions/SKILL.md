# Flow Ledger conventions

CLAUDE.md/AGENTS.md/GEMINI.md in this repo are Laravel Boost-managed and get
regenerated on `boost:install`, which drops anything that isn't part of
Boost's generic template. This skill is the durable record of that guidance.

## What this app is

Flow Ledger is a multi-tenant SaaS expense/cashbook management system:
branches/levels, cost codes, departments, currencies, cashbooks & cashbook
entries, payment requests and retirement requests routed through configurable
approval workflows (workflow templates/stages/instances/actions), cash counts
with denomination tracking, and staff/position records. Tenant-scoped models
live in `app/Models/Tenant`; permissions are defined per-domain-area in
`app/Enums/Tenant/PermissionKey` and `PermissionCategory` (Accounts,
Transactions, Workflow, Cashbook, Payment/Retirement Requests, etc.).

## Coding style (general — applies across all these Laravel projects)

- Work as a senior engineer: write idiomatic, readable, easily maintainable code.
- Don't add features, refactor, or introduce abstractions beyond what the task
  requires. Don't design for hypothetical future requirements. Three similar
  lines is better than a premature abstraction. No half-finished
  implementations either.
- Don't add error handling, fallbacks, or validation for scenarios that can't
  happen. Trust internal code and framework guarantees. Only validate at
  system boundaries (user input, external APIs).
- Every new PHP file starts with `declare(strict_types=1);`.

## Product design (SaaS defaults — general)

This is a multi-tenant SaaS product, not a bespoke single-customer deployment.
Default to SaaS assumptions when designing features, schema, or UX: tenant
isolation and data ownership boundaries, plan/tier or usage-based limits,
self-service onboarding, per-tenant configurability instead of hardcoded
behavior, and scaling to many tenants of varying size. For this app in
particular, keep workflow stages/approval routing and permission categories
tenant-configurable rather than hardcoded, since approval chains are exactly
the kind of thing that varies per-customer.

## Roles & permissions (ported convention)

Like the sibling `business` (biz-soft) project, this app has a CD guard that
syncs newly added `PermissionKey` cases onto the system admin role without
reverting permissions a tenant has intentionally revoked — i.e. permission
sync is additive-only, never destructive, on deploy. Preserve that behavior
if touching the permission-seeding/sync code path.

## Testing workflow

- Run a single test file or filter for quick feedback:
  `php artisan test --compact --filter=testName` (or via Sail if the project
  is running under Docker: `./vendor/bin/sail composer test -- --filter=testName`).
- Run the entire suite — prefer Test Impact Analysis for fast feedback:
  `./vendor/bin/sail composer test-tia`.
- If unsure whether TIA's change-impact cache might be giving a false pass,
  fall back to a full uncached parallel run: `./vendor/bin/sail composer test-parallel`.
- Pest TIA's cache lives inside the Sail container at `/home/sail` — it is
  wiped by `sail down` unless a `sail-home` Docker volume is mounted in
  `compose.yaml` to persist it across container restarts. If TIA suddenly
  runs the full suite instead of the fast incremental path after a restart,
  check that volume is still present before assuming something else broke.
